The Problem

Stage 1 auto-confirmed reservations

The initial chatbot collected booking details through slot-filling and immediately confirmed reservations. No human oversight — no way to refuse a booking when the lot is full, a date is blocked, or special circumstances require manual review.

Stage 2 Solution

🤖 Second LangChain Agent

The AdminAgent composes approval requests, delivers them through multiple channels, and interprets the administrator's free-text replies (approve/refuse with reason).

👤 Human Administrator

Sees pending reservations via web dashboard, terminal CLI, or optional email. Responds with plain language — the agent parses it into structured decisions.

Two-Agent Architecture

Key Stage 2 Components

AdminAgent

The second LangChain agent with three language skills: compose (turn reservation → approval request), escalate (deliver via tool-calling), interpret (free-text → structured decision).

EscalationService

Bridge between the two agents. User agent submits completed reservations; admin agent delivers them; decisions flow back through shared SQLite store.

Delivery Channels

LogChannel (always on), EmailChannel (optional SMTP), RecordingChannel (tests). All errors logged, never crash a turn.

Web Dashboard

GET /admin — real-time HTML UI listing pending reservations with Approve/Refuse buttons. Dark theme, auto-refreshes every 10s.

Admin CLI

python -m app.admin.cli — interactive terminal interface for approving/refusing reservations from the command line.

REST API

GET /admin/api/reservations lists pending. POST .../decision applies approve/refuse (requires token if configured).

AdminAgent: LangChain Implementation

Three Language Skills

1. compose_request()

prompt | DIAL chat | StrOutputParser
→ clear approval request

Offline fallback: template

2. escalate()

Tool-calling agent with
deliver_to_administrator tool

Offline fallback: direct delivery

3. interpret_decision()

DIAL with structured output (Pydantic):
  {approved: bool, reason: str}

Offline fallback: keyword parser
  - _APPROVE_WORDS, _REFUSE_WORDS, _REFUSE_PHRASES
  - ambiguous → refuse (safe default)

Configuration & Deployment

Required Settings

DIAL_API_KEY=     # empty = offline mode (both agents use deterministic fallbacks)
SQLITE_PATH=citypark.db

Optional Admin Settings

ADMIN_NAME=CityPark Administrator
ADMIN_EMAIL=       # if set, enables SMTP email escalation
ADMIN_TOKEN=       # if set, /admin/api requires ?token=...

Optional SMTP (activates when SMTP_HOST + ADMIN_EMAIL set)

SMTP_HOST=
SMTP_PORT=587
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=         # falls back to SMTP_USER
SMTP_USE_TLS=True
